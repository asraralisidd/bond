# Phase 9.5 — API Abuse Protection

## Threat model

Authenticated operator API handling sessions, collateral, risk,
attestation, andchain-adjacent transactions. Adversaries: credential
stuffing on session issuance, enumeration of public verification,
floods against mutations and expensive endpoints (risk analysis,
attestation evaluation, enforcement, transaction submission).
Rate limiting is defense-in-depth: authorization, idempotency, row
locks, and worker leases remain the real guarantees.

## Rate-limit architecture

`http/rate-limit/`: `store.ts` (`RateLimitStore` interface +
`MemoryRateLimitStore`), `policies.ts` (budgets + classification +
config), `identity.ts` (IP/operator/target keying + proxy rules),
`middleware.ts` (global + per-route factories), `registry.ts`
(per-app composition root). Policy is separate from storage: a
future shared store implements `RateLimitStore` with no route or
auth changes.

## Policy categories

| Policy                     | Budget (default) | Applies to                                                        |
| -------------------------- | ---------------- | ----------------------------------------------------------------- |
| auth                       | 30 / 10 min      | session issuance, keyed IP + credential target                    |
| public / publicEligibility | 200 / min        | unauthenticated verification, IP-keyed                            |
| read                       | 1000 / min       | authenticated GETs, IP baseline                                   |
| mutation                   | 200 / min        | agent/bond/attestor writes, operator-keyed                        |
| expensive                  | 100 / min        | risk analyses, eligibility writes                                 |
| attestation                | 60 / min         | quorum/decision/enforcement/verdicts, operator- or attestor-keyed |
| transaction                | 60 / min         | tx create/advance/confirm, operator-keyed                         |

Values are initial operational defaults (generous enough for
legitimate use), tunable via `RATE_LIMIT_*_MAX/_WINDOW_MS`.
Disabled entirely via `RATE_LIMIT_ENABLED=false`.

## Keying strategy

Operator requests: `op:{operatorId}`. Unauthenticated: `pub:{ip}`.
Auth attempts: `auth:{ip}:{target}` (target only, never the secret).
Verdicts: operator bucket when a session is present, else
`attestor:{id}`. Raw bearer tokens never become keys; secrets never
enter keys, responses, or logs.

## Trusted proxy behavior

`TRUST_PROXY` defaults to `false`: only the socket address is used.
When `true`, the first `X-Forwarded-For` entry is honored after
conservative validation, falling back to the socket address.
Invalid values fail startup. Deployments behind a CDN/LB must set
this deliberately; otherwise forwarded headers are ignored by
design (spoofable input must not drive bucketing).

## Response contract

HTTP 429 with the standard safe envelope
(`RATE_LIMITED`, fixed message, request id) plus `Retry-After`
(ceil seconds), `X-RateLimit-Limit`, `X-RateLimit-Remaining`.
Allowed responses also carry limit/remaining headers. No keys,
operator ids, secrets, or store internals leak.

## Configuration

Sixteen `RATE_LIMIT_*` variables (per-policy max + window for auth,
public, read, mutation, expensive, attestation, transaction, plus
`RATE_LIMIT_ENABLED` and `RATE_LIMIT_MAX_KEYS`) plus `TRUST_PROXY`,
all validated at startup (integer ranges, no NaN/negatives/absurd
magnitudes). Documented in `.env.example`.

## Memory-store limitations

Bounded at 10k buckets (configurable): expired entries swept first,
then oldest-inserted evicted — key-churn attackers evict each other,
never grow memory. **Process-local: each replica enforces
independently. Distributed production deployments require a shared
store behind `RateLimitStore`.** This limitation is structural and
stated, not hidden.

## Future Redis/shared-store migration path

Implement `RateLimitStore` (check-and-consume must stay atomic —
`EVAL`/Lua or equivalent), swap construction in `registry.ts`, keep
policies/identity/middleware untouched. No route or service changes.

## Authentication protection

Session issuance is covered by the strict auth policy, replacing the
old development-only per-process guard (removed, with its test
harness reference, to avoid two confusing layers). Success and
failure consume identically — no oracle. Production still fails
closed without wallet auth (unchanged).

## Public endpoint protection

Verification endpoints sit behind moderate IP budgets; enumeration
at scale trips 429s while legitimate use passes. `/health` and
`/ready` are exempt so platforms can always probe liveness.

## Expensive operation protection

Risk analyses, attestation evaluation/decision/enforcement, verdicts,
eligibility writes, and transaction mutations are limited before any
domain work runs (middleware order guarantees it).

## Frontend behavior

`friendlyMessage()` maps 429 to a calm notice; `DataState` and the
dashboard render it. No automatic retries anywhere — only explicit
user-initiated Retry buttons — so a limited client can never hammer
the API into a retry storm.

## Known limitations

In-memory store is per-process (see above); clock skew across hosts
would shift fixed windows (NTP assumed, as elsewhere); per-route
limits apply after authentication, so failed-auth floods rely on the
global baseline; verdict endpoints without sessions fall back to IP
keying.
