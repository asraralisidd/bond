# Phase 9.2 — PostgreSQL Reliability & Atomicity

## Transaction abstraction (`db/pool.ts`)

`withTransaction(fn)` checks out one client, runs `BEGIN`/body/`COMMIT`,
rolls back on any failure (rollback errors swallowed — the original error
wins), and always releases the client. No nested transactions: services
pass the client down instead. All stores already accepted an optional
`PoolClient`; the 10 mutating store functions that lacked the parameter
gained it, and every one of those threads it into its query call.

Rule now enforced in every mutating service (agents, bonds, risk,
attestations incl. verdicts/decisions, eligibility, transactions,
finalizers, reconcile): **state write(s) + protocol event(s) commit in
one transaction**. Pure computation (risk engine scoring, attestor
evaluation, adapter calls) stays outside transactions — connections are
never held across CPU work or network I/O (REAL confirm does its
finality check first, then opens the transaction).

## Atomic event behavior

`recordEvent(event, client?)` joins the caller's transaction. A failed
event write rolls back the domain mutation and vice versa; verified by
tests that force event failure (NOT NULL violation) and assert zero
rows in both tables. Event schemas and versions are unchanged.

## Migration advisory locking (`db/migrate.ts`)

The whole discovery/application pass runs inside one transaction holding
`pg_advisory_xact_lock(7272718288)`. Concurrent runners serialize; the
loser sees applied rows and runs nothing. The lock is transaction-scoped,
so it releases on commit, rollback, failure, or disconnect with no
cleanup path. Tested with two concurrent runners against a fresh
database: each migration applied exactly once.

## Pool hardening

`poolTuningFromEnv` with validated `PG_CONNECT_TIMEOUT_MS` (5000),
`PG_IDLE_TIMEOUT_MS` (30000), `PG_STATEMENT_TIMEOUT_MS` → pg
`query_timeout` (30000), `PG_POOL_MAX` (10). Invalid values throw at
startup. `pool.on('error')` logs a sliced message with no connection
string. Same keys added to `ApiConfig` and `.env.example`. Invalid
timeout config is covered by tests, including a credentials-leak
assertion on the tuning object.

## Row-lock strategy

- Transaction transitions (`advance`, `confirm`, worker `setTxStatus`)
  re-read the row with `SELECT … FOR UPDATE` inside the same
  transaction that validates and writes — check-then-act races between
  concurrent advancers are serialized; exactly one transition wins and
  exactly one event is recorded (tested).
- Idempotency needs no row locks: claim (INSERT…ON CONFLICT) and
  reclaim (conditional UPDATE) are each single atomic statements;
  losers re-read and converge.
- Bond/agent transitions keep optimistic validation + UNIQUE guards
  (one-live-bond partial index) with full event history, which makes
  last-writer-wins auditable rather than silent. Documented as
  acceptable: no silent divergence is possible.

## Idempotency TTL/lease model

`claimIdempotencyKey` now returns `claimed | replayed | conflict` plus a
`reclaimed` flag. Lease rules: completed+unexpired replays; completed+
expired, in-progress+expired (stale holder), and different-fingerprint+
expired are reclaimed via a single conditional UPDATE (losers re-read
and converge); in-progress+unexpired and failed always conflict
(failed requires a fresh key — no silent resurrection of failures).
TTL comes from validated `IDEMPOTENCY_TTL_HOURS` (default 24). Concurrent
identical requests converge to at most two executions with only
completed outcomes returned — tested without sleeps. `createTransactionIntent`
additionally catches unique-violation races on `idempotency_key` and
returns the winner's row instead of 500ing.

## Indexes (migration 008, forward-only)

`protocol_events(created_at)`, `risk_flags(agent_id, status)`,
`idempotency_keys(expires_at)`. Each serves an existing hot path
(audit reads, open-flag counts, TTL reclaim scans). Nothing speculative.

## Concurrency guarantees

- Same key + same request → single execution, replayed result.
- Same key + different request → 409, active or expired-original.
- Same transition twice concurrently → one wins (machine rejects the
  other), one event.
- Two migration runners → each migration once.
- Stale leases recover; active leases cannot be stolen (operator_id
  preserved — tested).

## Known limitations

- No statement-level READ COMMITTED anomalies beyond row locks are
  handled; REPEATABLE READ is not used (documented, unnecessary here).
- `failed` idempotency keys never auto-recycle (by design).
- Worker scheduling/retries/backoff remain Phase 9.4 (entry points and
  `attempts` column already exist).
- REAL confirm path executes adapter I/O outside the transaction by
  design; a crash between finality observation and the confirm write
  leaves SUBMITTED (retry-safe: re-confirm is idempotent via the
  terminal-state guard).

## Deferred to Phase 9.3/9.4

Auth redesign, wallet auth, rate limiting, worker scheduler + retries +
dead-letter, metrics, Docker/CI, collection endpoints. Nothing in 9.2
preempts those designs: finalizer signatures already take a client,
and the worker already funnels through `setTxStatus`.
