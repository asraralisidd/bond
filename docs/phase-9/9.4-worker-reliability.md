# Phase 9.4 — Production Worker, Job Processing & Retry Reliability

## Worker architecture

`apps/api/src/services/worker/`: `types.ts` (phases, failure classes,
stats, snapshot), `config.ts` (validated bounds), `backoff.ts`
(deterministic exponential backoff + stable per-job jitter),
`classify.ts` (RETRYABLE / PERMANENT / ALREADY_COMPLETED /
REQUIRES_RECONCILIATION), `claim.ts` (atomic batch claim),
`runtime.ts` (poll → claim → execute → persist, drain-aware loop),
`registry.ts` (one runtime per API process), `index.ts` (barrel).

Lifecycle: STARTING → RUNNING → DRAINING → STOPPED. `start()` is a
no-op when disabled or already looping; `stop()` drains active jobs
up to a bounded deadline, then stops; `runOnce()` performs one full
poll and is a no-op while draining/stopped. The worker is an execution
mechanism, not an authority: it runs persisted, authorized intents
through registered purpose executors and the Midnight Adapter only.

## Job states

The public domain lifecycle is untouched
(IDLE → … → CONFIRMED / FAILED). Operational coordination lives in
new nullable columns on `chain_transactions` (migration `009`):
`claimed_by`, `claimed_at` (lease), `next_attempt_at` (schedule),
`max_attempts` (default 5), `reconciliation_required`,
`dead_letter`. A row is claimable when PENDING, due, not
dead-lettered, not flagged, and unclaimed or lease-expired.

## Claim/lease model

One statement claims a batch: UPDATE…WHERE id IN (SELECT…FOR UPDATE
SKIP LOCKED) limited to configured concurrency, setting claim owner,
timestamp, and bumping attempts exactly once. Concurrent workers
divide rows without waiting; a crashed holder's lease expires and any
worker recovers the row. Claiming never holds a transaction open
across execution — network I/O always happens outside DB transactions.

## Retry classification and backoff

`classifyFailure`: DomainError / 4xx ApiError → PERMANENT;
unique/already-consumed/processed markers → ALREADY_COMPLETED;
uncertain-submission markers (including the worker's own REAL
no-wallet-attended-flow marker) → REQUIRES_RECONCILIATION; transient
network/timeout patterns and everything else → RETRYABLE (bounded,
never silent). Backoff: `min(max, base·2^(n-1))` plus a stable
SHA-256-derived jitter (0–999ms) per job id — deterministic across
restarts, spread across jobs. Exhausted or permanent failures become
FAILED + dead-lettered with an auditable event; retryable failures
reschedule `next_attempt_at` with their error recorded.

## Crash recovery

Leases expire (`WORKER_LEASE_MS`, default 60s); recovery is any worker
claiming an expired lease — proven by test (dead worker's job
completes under a new worker). Live leases are never stolen (tested).
Stats, not memory, are the source of truth throughout.

## Uncertain blockchain submission

The dangerous sequence (submit → crash → unknown outcome) is handled
by refusal to guess: if an executor throws after the call may have
reached the chain — or if REAL mode has no wallet-attended path at
all — the row is flagged `reconciliation_required` and excluded from
claiming. Resolution happens only through `confirmTransactionService`
against a recorded `chain_tx_id` (REAL with providers) or explicit
operator action; rows without a chain reference stay flagged for a
human. Statement: **a REAL submission followed by an uncertain
client/network outcome cannot be safely retried blindly**, and this
worker never does.

## Reconciliation

Each poll sweeps flagged rows (bounded) and, on its own interval,
runs the existing `runReconciliationOnce` (no second implementation)
for chain-vs-mirror healing. Confirm-sweeps only attempt REAL
confirms when providers exist; SIMULATED rows await explicit operator
confirmation by design and are counted, never touched. Stuck-SUBMITTED
rows are reported in the snapshot (`stuckSubmitted`).

## Executor/finalizer boundaries

Executors were audited: they map persisted intent → adapter SIM ops
using persisted attestation decisions only (`buildDecisionFromAttestation`
reads the authorized record). No `@bond/risk-engine` imports, no
attestor evaluation calls, no wallet material anywhere in the worker
path (source-scanned in tests). The worker executes decisions; the
attestor quorum makes them. Finalizers run only after confirmation,
inside the same transaction as the status write.

## Shutdown

`ShutdownDeps.onDrainStart` (additive, Phase 9.1 behavior otherwise
unchanged) stops the worker first: no new claims, active jobs drain to
the deadline, then server/pool close as before. Repeated signals keep
the force-exit path.

## Configuration

`WORKER_ENABLED` (default true; disabled is safe and supported),
`WORKER_CONCURRENCY` (5), `WORKER_POLL_INTERVAL_MS` (5000),
`WORKER_LEASE_MS` (60000), `WORKER_MAX_ATTEMPTS` (5),
`WORKER_BACKOFF_BASE_MS` (1000), `WORKER_BACKOFF_MAX_MS` (60000),
`WORKER_SUBMITTED_RECONCILE_AFTER_MS` (300000),
`WORKER_RECONCILE_INTERVAL_MS` (60000) — all validated positive
integers; invalid values fail startup. Documented in `.env.example`.

## Observability

Structured `worker:*` log events (started/stopping/stopped,
submitted, retry, dead-letter, uncertain, reconciled, reconcile,
poll failures) carrying only IDs and counts via the existing
allowlisted `LogContext`. Readiness exposes a safe `worker` section
(enabled/phase/running/draining/lastPollAt/activeJobs/lastError);
`/health` is unchanged. No metrics dependency added; stats object is
metrics-ready.

## Security boundaries (tested, not just documented)

Worker sources contain no risk-engine, attestor-evaluation, or wallet
imports (source scan); unknown purposes are rejected at intent
creation and dead-lettered without chain contact if they ever reach
the worker; SIMULATED mode is preserved end to end (never
auto-confirmed); public/private projections untouched.

## Known limitations

- REAL end-to-end submission/confirmation is coded but unexecuted
  here (needs funded wallet + devnet — same standing blocker as
  Phase 5/6); REAL jobs flag for reconciliation by design.
- `attempts` counts claim cycles plus status writes; treat
  `maxAttempts` as an upper bound on worker touches.
- Single-process loop; multi-replica is safe via SKIP LOCKED but
  untested beyond two workers.
- No per-purpose retry policies (one global budget); no dead-letter
  requeue API (insert a fresh intent instead).
- SIMULATED ledgers are per-handle memory; worker holds one
  long-lived handle per process.
